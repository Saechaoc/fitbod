The three chip rows (TimeRangeChipRow, BlockPhaseChipRow, MuscleChipRow) already used `ProgressFilterChip` — the BRU rectangular inverted-active chip built in Phase 6.1. This task replaced the two banned footer tokens:

## Deviations from Plan

### Intentional Plan B Decision (not a deviation — plan-authorized)

**Stacked-bar BRU intent palette — Plan B selected**

- **Found during:** Task 2 analysis
- **Issue:** UI-SPEC §Design Pivot #7 specifies BRU intent palette for stacked bars (strength=`bruInk`, hypertrophy=`bruInk@0.40`, deload=`bruMuted`). This requires each `MuscleSlice` in `WeeklyTonnageAggregator` to carry an intent field. The aggregator currently groups by `muscleID` / `muscleName` only — adding intent would require new data-path work through `WeeklyTonnageAggregator` and its call sites.
- **Decision:** Plan B — system color palette for muscle-stacked mode via `.foregroundStyle(by: .value("Muscle", slice.muscleName))`. BRU intent palette applied to the baseline (non-stacked) bar only.
- **Justification:** UI-SPEC §Design Pivot #7 explicitly provides this escape hatch: *"sketch fidelity lets the system palette stand for stacked muscle mode."* Extending the aggregator to carry intent is a new data-path change (Rule 4 architectural scope per deviation rules). Documented for future phase pickup.
- **Files modified:** `fitbod/Progress/WeeklyTonnageView.swift` (inline Plan B comment)
