# Phase 2 — UI Design Contract

> Visual and interaction contract for Core Loop (Routines + Sessions). Generated by `gsd-ui-researcher`, verified by `gsd-ui-checker`. **v2: BRU visual layer (2026-05-23)** — replaces the v1 native-HIG styling with the brutalist design system used across all `bru-screens/*.jsx` mockups.

This phase ships seven user-visible surfaces: a single-screen **RoutineBuilderView** with inline exercise search and per-exercise prescription editor; a **RoutinesListView** sectioned by folder; a **SessionLoggerView** with per-set inputs and inline "Previous" column; a **RestTimerLiveActivity** for the Dynamic Island and lock screen; an **ExerciseHistoryView** with intent-split filter chips; the **TodayView** root with block context, stat strip, week ticker, and the black-slab "Start workout" CTA; and a **SessionHistoryView** (intent-split list with weekly tonnage spark).

The design stance is **brutalist functional** — borrowed verbatim from the BRU mockups under `bru-screens/`. The aesthetic is the opposite of "comprehensive but uncluttered" Apple HIG: every surface is bounded by sharp 1.5pt or 2pt ink rules, color is restricted to three roles (ink / paper / signal) plus structural greys, typography is two faces (a heavy condensed display + a strict monospace) with explicit uppercase + letterspacing on every label, and rounded corners are forbidden. The Phase 1 UI-SPEC token set is **superseded** for phases 2+ — every Color asset and Typography role from `01-UI-SPEC.md` is replaced by the BRU token names below.

The implemented iOS code at the time this revision is written predates BRU and uses default Apple system styling. **All visual surfaces touched by Phase 2 must be rewritten to BRU tokens.** Interaction logic (snapshot pattern, rest-timer engine, navigation paths, copywriting) is preserved verbatim from v1 and is not in scope for this revision.

## Design System

| Property | Value |
|----------|-------|
| Tool | none (native SwiftUI — `components.json` / shadcn not applicable to iOS) |
| Preset | not applicable |
| Component library | SwiftUI built-ins (`VStack`, `HStack`, `Grid`, `LazyVStack` in `ScrollView`, `NavigationStack`, `Sheet`, `EditMode` + `.onMove`, `.searchable`, `Stepper`, `Picker`, `TextField`, `.confirmationDialog`, `.alert`, `Menu`) + Apple `ActivityKit` (rest-timer Live Activity / Dynamic Island) + custom **BRU primitives** (see "Component Inventory" below — `BRUChip`, `BRUDisplay`, `BRUReadout`, `BRUSectionHead`, `BRUButton`, `BRUSpark`, `BRUTabBar`, `BRUHeaderBar`, `BRUDivider`) — these replace shadcn-style component primitives with the brutalist contract drawn from `bru-screens/*.jsx` |
| Icon library | **None.** SF Symbols are NOT used in BRU. Glyphs come from: (a) typographic characters in the display/mono fonts (e.g. `‹ Back`, `▸`, `★`, `↑`, `↘`, `▲`, `•••`, `⋮⋮`), (b) custom rectangle / line / progress-arc shapes drawn with `Rectangle`, `Path`, `Canvas` — never SF Symbols. The Phase 1 SF Symbol roster (`figure.strengthtraining.traditional`, `list.bullet.rectangle.portrait`, `play.fill`, etc.) is **deprecated** and must be removed when surfaces are rewritten to BRU. |
| Font | **Two faces, bundled as app resources.** (1) `BRUDisplay` — a heavy condensed grotesk (e.g. **Space Grotesk Bold** or **Anton Regular**) for all headings, hero numerics, single-digit set indices, and CTA emphasis. (2) `BRUMono` — a fixed-pitch monospace (e.g. **JetBrains Mono Regular / Bold** or Apple `.monospaced(.body)` as a fallback) for ALL tabular numerics (weight × reps @ RPE), labels with letterspacing, and any rendered code-like data. Body text and chip labels use `BRUMono` weight 600. **No SF Pro, no Apple semantic Dynamic Type styles** — sizes are explicit pt values, mapped through a centralized `BRUFont` enum so a future Dynamic Type adoption is one edit. |

**Why "bundled fonts, not Dynamic Type":** the BRU aesthetic depends on the specific terminal-feel weight + letterspacing of a heavy condensed display paired with a precise monospace. Apple system fonts (SF Pro Display, SF Mono) approximate this but visibly soften the brutalism (SF Pro has a humanist warmth, SF Mono is too thin at small sizes). Per the orchestrator directive ("iOS app is an EXACT REPLICA of the BRU mockups"), font fidelity is non-negotiable.

**Stack constraint reconciliation:** `CLAUDE.md` locks out third-party **SPM** dependencies. Bundling `.otf` / `.ttf` files in `fitbod/Resources/Fonts/` and declaring them in `Info.plist` under `UIAppFonts` is NOT an SPM dependency — it is a resource-file inclusion, fully compatible with the stack constraint. Two recommended pairings (developer to confirm during executor wiring):

| Pairing | Display | Mono | License | Why |
|---------|---------|------|---------|-----|
| **A (recommended)** | Space Grotesk Bold / SemiBold | JetBrains Mono Regular / Bold | OFL (free, commercial-ok) | Most-cited brutalist-friendly pair in modern design systems; both ship as `.otf` from Google Fonts; total bundle weight ≈ 1.2 MB |
| B (fallback) | Anton Regular | JetBrains Mono Regular / Bold | OFL | Anton is more aggressive (ultra-condensed) — matches mockups' "display" character better but only ships one weight; pair with a separate semibold for body emphasis |
| C (zero-bundle escape hatch) | system `Font.system(size:, weight: .black, design: .default).width(.compressed)` | system `Font.system(size:, weight: .semibold, design: .monospaced)` | n/a | If bundling fonts is rejected; the brutalism softens visibly but the spec still ships |

**Locked decision for v2:** Pairing **A**. The executor includes both `.otf` files under `fitbod/Resources/Fonts/`, declares them in `Info.plist` under `UIAppFonts`, and exposes them through `BRUFont` (see "Typography" below). If a license review later prefers pairing B or C, the swap is a one-file edit to `BRUFont.swift`.

**Status bar / chrome:** the BRU mockups render an iPhone status bar through a `BruPhone` wrapper (a small status-bar pill at the top). On iOS this is automatic via `NavigationStack` chrome — but the BRU style requires a 2pt ink hairline directly below the safe-area inset and replaces the default navigation bar with a custom `BRUHeaderBar` (left action + center title + right action, all-caps, ink-on-paper, no system tinting). The existing `RootView` `TabView` is preserved structurally but its `TabView.tabBar` is replaced with `BRUTabBar` (see Component Inventory). **The existing `RootView.swift` keeps its `NavigationStack`-per-tab architecture from Phase 1; only the chrome decoration is replaced.**

## Spacing Scale

Multiples of 4, iOS 8-point grid. The scale itself carries forward from v1 — BRU's brutalism does not change spacing primitives, only how they're applied (denser tables, sharper borders, more uppercase-letterspaced labels).

| Token | Value | Phase 2 usage in BRU |
|-------|-------|----------------------|
| xs | 4pt | Chip-internal horizontal padding, gap between chips in a chip row (per BRU mockups: `gap: 4`–`6`), grid-cell gap inside a stat strip, week-ticker cell gap |
| sm | 8pt | Inter-row content stack inside a card, chip-to-display gap, "Sub-reps:" sub-rep chip spacing, padding between hero number and its caption inside the black slab |
| md | 12pt | Vertical padding of compact list rows (per BRU mockups: `padding: '11px 16px'` or `'12px 16px'` — rounded to 12pt), prescription chip-row top margin, inter-section content stack |
| lg | 16pt | Horizontal screen inset (every BRU mockup uses `padding: '... 16px'`), padding inside the black-slab CTA, padding inside header band, padding inside section-head row |
| xl | 24pt | Bottom safe-area filler beneath the bottom bar on routine builder (`height: 24, background: BRU.bg`), spacing between session-summary block and exercise list |
| 2xl | 32pt | Empty-state top spacing (e.g. "No routines yet" heading on a clean install), gap above empty-state action text button |
| 3xl | 48pt | Reserved for stretched empty states on tall devices; not used in the bru-screens mockups but kept for forward use |

**Exceptions (load-bearing for iOS HIG and BRU brutalism):**

- **44pt minimum touch target** for every tappable control. Specifically: each per-set checkmark, each RPE chip in the inline RPE row, each ±15s button on the rest timer, every drag handle (`⋮⋮` glyph) in the routine builder, every intent-filter chip on the history view, every day tab in the routine builder's day-strip. Visible content may be smaller (e.g. a `BRUChip` capsule is ~22pt tall) but `.contentShape(Rectangle()).frame(minHeight: 44)` extends the hit area.
- **Set-row completion glyph** is a 22pt visual (a small ink square that fills when complete — see `SetCompletionGlyph` below) but 44pt hit area.
- **Rest-timer overlay collapsed pill** is 64pt tall and full-bleed below the header — NOT a floating pill anymore. The BRU equivalent of "Dynamic Island over a tab bar" is a full-bleed ink slab anchored above the BRUTabBar with `.title2` countdown.
- **Live Activity** layouts follow Apple's `ActivityKit` dimensions strictly — compact ≤ 116pt wide trailing, minimal = 22pt circle. The BRU palette (ink background + paper text + signal progress arc) is applied within those bounds.
- **Border widths are spacing-adjacent tokens:** 2pt for section-level ink rules (between top stat strip and block context, between block context and black-slab CTA, around the inner set-rows container, around the +Add Exercise dashed slot, around the bottom action bar); 1pt for hair-rule dividers between consecutive list rows; 1.5pt for inner border on week-ticker cells and superset brackets. These are FIXED — never approximate to "default thin" or use `.divider()` (which renders at sub-pixel hairline). Use `Rectangle().fill(.bruInk).frame(height: 2)` or `Rectangle().stroke(.bruInk, lineWidth: 2)` explicitly.

### Project-Level Spacing Scale Extension

The BRU project standard spacing set is `{4, 8, 12, 16, 24, 32, 48, 64}` — an extension of the dimension-5 checker default `{4, 8, 16, 24, 32, 48, 64}` by adding **12pt**.

**Rationale:** BRU mockups heavily use 12pt as the compact-row vertical rhythm (e.g. `padding: '12px 16px'` on `BlockPhaseEditorRow` rows, `padding: '11px 16px'` on compact list rows). Without 12pt, every compact list row collapses to 8pt (too dense for text legibility) or expands to 16pt (breaks the BRU tight-block aesthetic that distinguishes it from standard iOS list spacing). 12 is a multiple of 4, so the underlying multiple-of-4 invariant is preserved — this is an additive extension, not an exception to the base rule.

**Constraints:**
- Per-phase UI-SPECs MUST use the extended set `{4, 8, 12, 16, 24, 32, 48, 64}` and MUST NOT introduce values outside it.
- 44pt touch-target and other iOS HIG platform constants are exempt from this rule (they are not layout-spacing tokens).
- Fixed visual containers sized to match mockup measurements (e.g., 56pt timeline bar, 28pt week-ticker cell height) are exempt as they are component-dimension constants, not layout-spacing tokens.
- This extension is locked project-wide. All phase UI-SPECs inherit it.

### Project-Level Design System Exemption — Type Scale

The BRU 7-role type scale (`displayHero`, `displayLarge`, `displayMedium`, `bodyEmphasis`, `bodyDefault`, `labelSmall`, `labelMicro`) is a **locked project primitive**.

**Status:** Phase 4 surfaced that Phase 2's `02-UI-SPEC.md` declares 6 roles and Phase 4 pattern-matches 7 (the existing 6 plus `labelMicro` which appeared in Phase 2 component specs). The canonical count across the BRU design system is **7 roles**. The table above lists 6; `labelMicro` (7–9pt Mono Bold, 1.0–1.2 letterspacing, UPPERCASE) was always present in practice — see the `BRUFont` enum init signature in §Component Inventory which explicitly includes `labelMicro`. This section formalizes the 7-role count as the locked BRU baseline.

**Rationale for the dimension-4 waiver:** The checker's "max 4 type roles" rule exists to prevent ad-hoc per-phase font accumulation. The BRU 7-role scale is a deliberate, project-wide design system foundation — not ad-hoc growth. It applies system-wide in the same way that border-width constants and the 44pt platform touch-target are exempt from spacing-grid rules. The 7 roles are the complete vocabulary; no phase may add an 8th.

**Constraints:**
- Per-phase UI-SPECs MUST NOT introduce new roles beyond these 7. They MAY use any subset.
- This exemption is the basis for dimension-4 compliance project-wide. The checker should treat the 7-role scale as one cohesive design-system primitive, not as 7 independent ad-hoc sizes.
- Any future type need must land in one of the existing 7 roles by adjusting size within the declared range, not by adding a new role.

### Accent reserved for (Phase 2 surfaces)

**Replaces the v1 17-item accent list entirely.** BRU restricts `bruSignal` to the following Phase 2 surfaces. Every other interactive element uses ink-on-paper or paper-on-ink — never signal.

**Explicitly NOT accent:**

- Drag handle (`⋮⋮` glyph) — `bruMuted`, never signal.
- Inactive day tabs in routine builder — `bruPaper` background, `bruInk` text.
- Set-type chips W/UP and WORK and BACK — `bruInk` outline + label. Only TOP and the progression-kind chip get signal.
- "+ Add Exercise" dashed-border slot at bottom of routine builder — `bruInk` 2pt dashed border, `bruInk` label, `bruMuted` "↘ FROM LIBRARY" hint. NOT signal — adding an exercise is structural, not aspirational.
- "Discard" button in the bottom action bar — ghost variant (transparent fill, `bruInk` text, `bruInk` top border). NOT destructive red, NOT signal — neutral is correct because BRU has no `systemRed`.
- Section-head right-side metadata (`Tap to reorder`, `${sessions.length} sessions`, `WHAT'S NEXT`) — `bruMuted` `labelSmall`. NOT signal.
- "Previous" column data in session logger — `bruMuted` `bodyDefault`. NOT signal — it's a reference, not a CTA.
- Pinned-note inline pill — `bruInk` outline 1.5pt + `bruInk` text on `bruBg2` fill. The pin glyph (a small ink square) is `bruInk`. NOT yellow-system, NOT signal.
- Set-type chips on the BRU-replaced session logger — the system-colored capsules from v1 (blue / orange / red / purple per type) are **deprecated**. BRU replaces them with uppercase letterspaced `labelSmall` text inside ink-outlined chips. The semantics are encoded by the WORD ("DROP", "FAILURE", "REST-PAUSE") not by color. Only the "TOP" set gets a signal tint (per spec item 8).

### Destructive

There is NO `bruDestructive` token. The BRU stance is that destructive actions are conveyed by the **word** ("Discard", "Delete", "Remove from Session") and the **placement** (left-side ghost button in the bottom bar; trailing context-menu item with an explanatory `confirmationDialog`), not by a system-red color. The Apple HIG affordance of "destructive button text in red" is REPLACED by `bruInk` text inside a `confirmationDialog` whose body explains the consequence in plain copy. The system `.alert(role: .destructive)` modifier may render iOS's red `Destructive` button styling — this is acceptable as the only place red appears in Phase 2, and it falls inside Apple's `.alert` chrome which BRU cannot override. **No view in Phase 2 explicitly renders `Color.red` / `Color(.systemRed)`.**

## Accessibility Contract

The user is the only user and is sighted, but iOS accessibility behaviors come "for free" with native SwiftUI and breaking them would be self-sabotage. The Phase 1 accessibility contract applies as a baseline; Phase 2 BRU adds the following:

| Surface | Contract |
|---------|----------|
| Drag handle (`⋮⋮` glyph) | `accessibilityLabel` = "Reorder {exercise name}". `accessibilityHint` = "Double-tap and drag to reorder". Native SwiftUI `.onMove` handles VoiceOver Rotor automatically. |
| `SetCompletionGlyph` | `accessibilityLabel` = "Mark set {N} complete" / "Set {N} complete". `accessibilityTraits` = `.button` + `.isSelected` when complete. |
| Intent filter chip | `accessibilityLabel` = "{intent name} filter, {currently selected / unselected}". Selected: `.isSelected` trait. |
| RPE chip row | Each chip: `accessibilityLabel` = "RPE {N}". `accessibilityHint` (first chip only) = "Double-tap and hold for decimal RPE". |
| `BRUChip` | `accessibilityLabel` = chip's visible text (un-uppercased for VoiceOver clarity — e.g. "Strength" not "STRENGTH"). UPPERCASE rendering is purely visual via `.textCase(.uppercase)`; the underlying string is mixed-case. |
| `BRUDisplay` (numeric values) | `accessibilityLabel` = the value text, plus its label context (e.g. "Day streak, 14" instead of just "14"). |
| `BRUSectionHead` | `accessibilityAddTraits(.isHeader)`. |
| `BRUTabBar` | Each tab: `accessibilityLabel` = tab name, `accessibilityHint` = "Double-tap to switch tabs". Active tab: `.isSelected` trait. |

Below `xLarge` and above `xxLarge` the contract is "render at the BRU pt sizes scaled by the system's Dynamic Type ratio". This is a *graceful* scaling — not full Dynamic Type adoption (which would replace the BRU sizes entirely). |

Dark-mode equivalents are verified to clear the same thresholds via the inverted palette. |

## What's Explicitly Deferred (so the checker doesn't fail it for absence)

The deferred list from v1 is preserved verbatim — BRU is purely a visual rebuild, and the phase scope is unchanged. Additional BRU-specific deferrals:

- **Phase 5 fatigue surfaces (heatmap, MEV/MAV/MRV bars, volume bars)** are NOT rewritten to BRU in this revision. They remain on Phase 1 / 5 native-HIG styling until a future Phase 5 UI-SPEC revision. The `VolumeProductiveGreen` / `Amber` / `Red` / `BelowMEVGray` colorsets remain valid for those views only.
- **Phase 6 progress chart surfaces (`ExerciseProgressView`, `WeeklyTonnageView`, etc.)** are NOT rewritten in this revision. They will adopt BRU when Phase 6 ships its own UI-SPEC revision.
- **Phase 4 block surfaces (`BlockBuilderView`, `BlockReviewView`)** are NOT rewritten in this revision — they stay on whatever styling Phase 4 shipped. A `bru-screens/block-builder.jsx` mockup exists for a future Phase 4 UI-SPEC revision.
- **Settings tab** is NOT rewritten in this revision — `bru-screens/settings.jsx` is the future contract; rewriting Settings lands when its phase is next touched (likely Phase 6 polish revision).
- **Custom exercise editor** styling is NOT rewritten — `bru-screens/custom-exercise.jsx` lands in a future Phase 1 UI-SPEC revision.
- **Existing `IntentChip.swift` implementation** uses the deprecated `Color.accentColor` teal. As part of the Phase 2 BRU rewrite, `IntentChip` is updated to use `bruInk` outline + `bruSignal` fill for `.strength` intent, `bruInk` outline for all other intents. The accessibility label and structural API are preserved.
- **Landscape orientation polish** (Phase 6 polish) — BRU mockups are portrait-only; rotation allowed but no BRU-specific landscape layouts in this revision.
- **Bundled-font fallback if license review rejects pairing A** — the spec's `BRUFont` enum is structured so a font swap is a one-file edit. The fallback to pairing C (system fonts with `.compressed` width + `.monospaced` design) is a one-commit revert; copy and layout will not need changes.
- **Light/Dark mode parity validation** — the BRU mockups show only light mode. The dark-mode hex values in the color table above are derived by inverting ink↔paper and applying a +10% L shift to signal. The executor builds dark variants of all 8 color sets; a UAT pass in dark mode is deferred to the verifier round.
- **Dynamic Type scaling beyond `xxLarge`** — BRU at `accessibility3` and above will have visible layout reflow (set-row cells flowing to two lines, RPE chip row scrolling horizontally). This is acceptable for v1 because the user is the only user and uses default Dynamic Type. Full accessibility Dynamic Type polish is deferred.
- **Live Activity dark-mode tinting** — Apple's `ActivityKit` chrome wraps activities in system-tinted containers that may visually clash with the brutalist palette. If this becomes a problem in physical-device testing, the workaround is to set `ActivityKit` `activityBackgroundTint(_:)` to `Color.bruInk` and let the system handle text contrast.
