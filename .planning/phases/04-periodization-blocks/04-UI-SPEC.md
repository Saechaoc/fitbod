# Phase 4 — UI Design Contract

> Visual and interaction contract for Periodization & Blocks. Generated by gsd-ui-researcher. **v3: checker-compliance fixes (2026-05-23)** — typography waiver, spacing conformance corrections (6pt→4pt, 14pt→12pt), and copywriting empty-states additions. All BRU design tokens and interaction contracts from v2 are preserved verbatim.

This phase delivers **defined mesocycles with deterministic phase progression and a transparent home-screen timeline**. The primary new surfaces are: a `BlockBuilderView` with an inline phase timeline visual + ordered phase rows; a "Blocks" section on `RoutinesListView`; a `BlockCard` on the Today tab with a horizontal-swipe week pager; a deload-week banner; a `BlockReviewView` sheet; a `ConsiderDeloadBanner` scaffold; and a "Block" picker chip in the `RoutineBuilderView` header.

The design stance is **brutalist functional** — identical to Phase 2/3. The BRU aesthetic governs all new Phase 4 surfaces: sharp 1.5–2pt ink rules, three-role color (ink / paper / signal), two-face typography (display + mono), UPPERCASE + letterspacing on all labels, zero rounded corners.

**Token inheritance:** For the full BRU token specification (color hex values, font faces, weight table, spacing scale, border widths, 60/30/10 split definition, `bruSignal` reserved-for master list), see `02-UI-SPEC.md` §Design System, §Typography, §Color. This document specifies Phase 4 surface-specific DELTAS only — everything not mentioned here is inherited verbatim from `02-UI-SPEC.md`.

## Spacing Scale

**Carries forward verbatim from `02-UI-SPEC.md §Spacing Scale`.** Standard set extended to include 12pt per `02-UI-SPEC.md §Project-Level Spacing Scale Extension`. No new tokens beyond that documented extension. Phase 4 surface-specific usage notes only:

| Token | Value | Phase 4 usage |
|-------|-------|---------------|
| xs | 4pt | Gap between chips in the block-builder header chip row (`BruChip` gap ≈ 5–6pt per mockup — round to 4); gap between week-column labels below timeline bar (`W1`, `W2` …); grid-cell gap inside the phase-data 3-column grid (`WEEKS / VOL / INT`) |
| sm | 8pt | Gap between phase-chip label and `NOW` chip in a phase row; vertical gap between block-name display and the status chip row in `BlockBuilderView` header; gap between `BlockReviewView` metric columns in the hero band (SESSIONS / TONNAGE / PRS) |
| md | 12pt | Vertical padding of each `BlockPhaseEditorRow` (`padding: '12px 16px'` per mockup); vertical padding of the week-swipe carousel section; internal padding of the e1RM row in `BlockReviewView`; padding of the fatigue-advisory strip at the bottom of `block-overview.jsx` |

**Phase 4 specific exceptions (load-bearing):**

- **44pt minimum touch target** carries forward for all tappable controls. Phase-chip `Menu` trigger inside `BlockPhaseEditorRow` must have `.contentShape(Rectangle()).frame(minHeight: 44)` even though the chip visual is ~28pt. Drag handles (`⋮⋮` glyph) are 44pt hit area.
- **Timeline bar height:** The `TIMELINE` visual in `BlockBuilderView` is 56pt tall (`height: 56` per `block-builder.jsx` line 28). This is a fixed visual container — it does NOT expand with Dynamic Type. Phase names inside bars use `labelMicro` (9pt) so they always fit.
- **Phase-data grid cells:** The 3-column `WEEKS / VOL / INT` grid in each `BlockPhaseEditorRow` uses `border: 1px solid BRU.ink` cells with `padding: '4px 8px'` (4pt vertical / 8pt horizontal). Rounded from mockup's `6px 8px` to the nearest standard token (`xs=4pt` vertical) to maintain grid conformance; visual density delta is negligible. These are display cells, not 44pt touch targets — the Stepper interaction for each field must be wired to a separate 44pt tap area or inline `Stepper` affordance.
- **Block hero band in `BlockOverviewScreen`:** The full-bleed ink band at the top of `block-overview.jsx` uses `padding: '12px 16px'` (12pt vertical / 16pt horizontal). Rounded from mockup's `14px 16px` to `md=12pt` vertical for grid conformance; the ink band reads identically at 12pt vs 14pt. The display text is `displayHero` 42pt. This band uses `bruInk` fill, `bruPaper` text — same as the Today-tab black slab.
- **Week ticker cell height:** 28pt visual (`height: 28` per `today.jsx` line 39), same as Phase 2's week-ticker on TodayView. This carries forward.
- **Border widths (unchanged from Phase 2):** 2pt for section-level ink rules; 1pt for hair-rule row dividers. The timeline bar outer border is 2pt (`border: 2px solid BRU.ink`). The per-phase-data grid cells use 1pt borders.

### Phase color palette (Phase 4 — inline code enum, NOT new asset catalog entries)

The four `BlockPhaseKind` cases are used for: timeline bar fills, phase chip fills, current-phase row tint, and the `NOW` chip. The palette is expressed as a `BlockPhaseColors` Swift enum (not in `Assets.xcassets`) — this matches the brutalist stance of keeping the palette in code where it is diff-friendly.

| Phase | Timeline bar fill | Row tint background | Chip fill (NOW state) | Visual intent |
|-------|------------------|--------------------|-----------------------|---------------|
| Accumulation (DONE/past) | `bruInk` (`rgba(10,10,10,0.85)`) — solid dark fill for completed phases | — | — | Past phase = "done, locked in" |
| Intensification (NOW) | `bruSignal` (#FF5C1A) | `bruSignal` at 6% opacity (`${BRU.signal}0F`) | `bruSignal` fill + `bruPaper` text | Current phase = signal warm-orange, unmissable |
| Realization / Peak (future) | `bruInk` at 25% opacity (`rgba(10,10,10,0.25)`) | `bruPaper` (no tint — upcoming is neutral) | `bruInk` outline chip | Future phase = quiet, not yet relevant |
| Deload (future scheduled) | Striped: `repeating-linear-gradient(45deg, transparent 0 6px, rgba(10,10,10,0.18) 6px 12px)` | `bruPaper` (no tint) | `bruSignal` outline chip (deload badge draws attention) | Deload = diagonal hatching = "rest zone" |

**SwiftUI implementation of the diagonal-stripe fill:** Use `Canvas { context, size in ... }` with a `Path`-based diagonal stripe pattern, or approximate with `Color.bruInk.opacity(0.18)` over an angled `LinearGradient` with hard stops. The exact pattern is: 45-degree diagonal stripes, alternating transparent (6pt) and ink-18% (6pt). This maps 1:1 to the `repeating-linear-gradient` in `block-builder.jsx`.

**No new color asset catalog entries** for phase colors — the enum is the source of truth.

### The `BruButton kind="signal"` variant (Phase 4 CTA pattern)

Width split: equal 1fr / 1fr. Separator: 2pt `bruInk` vertical rule between the two buttons. Outer container: 2pt `bruInk` top border, 0pt bottom (safe-area filler handles bottom). Height: `BRUButton kind="md"` = 48pt tappable area.

### Destructive actions (BRU v2 update)

The v1 spec used `Color(.systemRed)` for destructive labels. Per `02-UI-SPEC.md §Color §Destructive`: **BRU has no `bruDestructive` token.** Destructive intent is conveyed by word placement and the confirmation dialog body copy, NOT by color. The Apple `.alert(role: .destructive)` modifier is still permitted (it applies iOS-native red button styling inside the system alert chrome — BRU cannot override that). **No Phase 4 view explicitly renders `Color.red` / `Color(.systemRed)` outside of an alert action button.** The following Phase 4 destructive actions follow this rule:

| Action | Surface | Confirmation approach |
|--------|---------|----------------------|
| Delete a block | `RoutinesListView` swipe-to-delete | `.alert` with body "Linked routines stay; sessions logged under this block keep their snapshot context." → "Delete" (`.destructive` role — system renders red) / "Cancel" |
| End a block early | `BlockCard` overflow menu → "End Block" | `.alert` → "End Block" (`.destructive` role) / "Cancel" |
| Activating a new block (deactivates current) | `BlockBuilderView` "Active block" toggle | Inline `labelSmall` `bruMuted` caption — NOT a modal. The word "replace" signals consequence; no color signal needed. |

## Interaction Patterns

The following interaction contracts from v1 are **preserved verbatim**. Only rendering details change in v2.

**`BlockCard` week pager:** `TabView(.page(indexDisplayMode: .never))`. The BRU today.jsx shows a simple week-ticker strip on the main Today screen — the full pager UI lives on the dedicated `BlockOverviewScreen`. The Today-tab BlockCard is the compact strip form; tapping it pushes `BlockOverviewScreen`. This is a v2 clarification: the compact TodayView form (week ticker + phase chip + block name) is distinct from the full `BlockOverviewScreen`.

**`BlockBuilderView` phase-kind picker:** User taps the phase chip; a `Menu` opens with four options. Auto-applies RP-default multipliers per D-10 on kind change. The BRU chip tap opens a standard iOS `Menu` (no custom popover). The menu title is the current phase kind; options are the four `BlockPhaseKind` cases in `labelSmall` UPPERCASE inside the menu.

**`BlockReviewView` e1RM progress bar:** The horizontal bar is rendered with `GeometryReader` + two `Rectangle` fills: `bruInk` from 0 to the computed `pct * width`, then a 3pt `bruSignal` vertical cursor mark at `pct * width`. Not a SwiftUI `ProgressView` — use `Canvas` or `ZStack` with `Rectangle` shapes for exact BRU control.

**Single-active block invariant + other interaction flows:** Unchanged from v1 spec. See v1 §Interaction Patterns for `BlockReviewView` trigger/acknowledgment flow, `RoutineBuilderView` block picker flow, deload-week banner visibility, `ConsiderDeloadBanner` advisory flow, and snapshot pattern extension. All BRU rendering, no logic changes.

**Reduced motion:** The `TabView` page-swipe in `BlockOverviewScreen` is gated on `@Environment(\.accessibilityReduceMotion)` — when true, week navigation snaps without slide animation. The timeline bar fill animation (if any is added for the "past/now/future" fill states) must also respect reduce-motion.

### `BlockPhaseColors` Swift enum (inline — NOT asset catalog)

```swift
// fitbod/Periodization/BlockPhaseColors.swift
// Phase color palette — expressed in code, not in Assets.xcassets.
// The timeline bar fills use inline rgba values per block-builder.jsx.
// The chip/row tints use these values.
public enum BlockPhaseColors {

    // Full-opacity phase chip fill color
    public static func color(for kind: BlockPhaseKind) -> Color {
        switch kind {
        case .accumulation:    return Color("bruInk")           // past phase = solid ink
        case .intensification: return Color("bruSignal")        // now = signal orange #FF5C1A
        case .realization:     return Color("bruInk").opacity(0.25)  // upcoming = quiet
        case .deload:          return Color.clear               // stripe pattern — not a solid fill
        }
    }

    // 6% opacity row tint for the currently-active phase row
    public static func rowTint(for kind: BlockPhaseKind) -> Color {
        switch kind {
        case .intensification: return Color("bruSignal").opacity(0.06)
        default:               return Color.clear
        }
    }

    // Chip fill for the NOW state inside a phase row
    // (used for BRUChip when the phase is current)
    public static func nowChipFill(for kind: BlockPhaseKind) -> Color {
        return Color("bruSignal")   // always signal for NOW regardless of kind
    }
}
```

The **diagonal stripe** for the deload timeline bar is NOT a `Color` — it is a `Canvas`-drawn pattern or a `Rectangle` with a `repeating linear gradient` equivalent. The executor renders it with:

```swift
// SwiftUI approximation of repeating-linear-gradient(45deg, transparent 0 6px, rgba(10,10,10,0.18) 6px 12px)
Canvas { context, size in
    let stripeWidth: CGFloat = 12
    var x: CGFloat = -size.height  // start off-screen to the left to cover all angles
    while x < size.width + size.height {
        let path = Path { p in
            p.move(to: CGPoint(x: x, y: 0))
            p.addLine(to: CGPoint(x: x + 6, y: 0))
            p.addLine(to: CGPoint(x: x + 6 + size.height, y: size.height))
            p.addLine(to: CGPoint(x: x + size.height, y: size.height))
            p.closeSubpath()
        }
        context.fill(path, with: .color(Color("bruInk").opacity(0.18)))
        x += stripeWidth
    }
}
```
