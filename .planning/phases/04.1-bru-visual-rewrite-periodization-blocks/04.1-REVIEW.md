# Phase 04.1: Code Review Report

**Reviewed:** 2026-05-25
**Depth:** standard (per-file analysis with Swift/SwiftUI-specific checks)
**Files Reviewed:** 27 (21 source + 6 test files. `BRUHeaderBar.swift` was loaded even though it sits outside the explicit `files:` list; the agent's mandatory-read block requested it.)
**Status:** issues_found

## Summary

The BRU re-skin is broadly well-executed: BRU primitives are uniformly applied, the 25-pattern audit is satisfied, D-14 reduced-motion gate and D-15 accessibility labels are in place, and `BlockOverviewScreen.weekCarousel` is driven by a real `@Query<Session>` predicate (B5 fix verified — no hardcoded mocks). However, the review surfaces three correctness defects that affect rendered behavior (not just styling): the week-carousel uses a Calendar-locale-dependent `weekStart` paired with a hardcoded Monday-first weekday letter array, `BlockOverviewScreen.phaseRow` ships an orphan `ZStack` that renders a stray rectangle above each phase row, and `BlockOverviewScreen` captures `weekStart/weekEnd` once at `init` so the carousel will silently drift to a stale week if the view stays mounted across midnight (or week rollover). Several Warning-level issues cluster around `BlockOverviewScreen` (date math, `doneCount > scheduledCount` masked by `max(_:_:)`, predicate ignores `sourceRoutineID` matches in the past-week-via-rebuild case) and around `BlockBuilderView` (magic-number `frame(height: count * 120)` for the inner List). Tests cover behavior at the right level but the regression suite is source-text grepping rather than view-rendering — none of the Critical findings would be caught by the existing tests.

## Critical Issues

### CR-01: `BlockOverviewScreen` week carousel labels are off by one day in locales whose `Calendar.firstWeekday != 2`

**File:** `fitbod/Periodization/BlockOverviewScreen.swift:64` and `:348`
**Issue:** `weekStart` is computed via `cal.dateInterval(of: .weekOfYear, for: now)?.start`, which returns the week start using the current calendar's `firstWeekday`. The fitbod default `Calendar.current` on a US/`en_US` device returns **Sunday** as `firstWeekday=1`. The grid then hardcodes `let weekdayLetters = ["M", "T", "W", "T", "F", "S", "S"]` (Monday-first) and indexes by raw `offset` from `weekStart`. Result on en_US: the column drawn under the label "M" actually represents **Sunday**, "T" represents Monday, etc. — the entire row is shifted by one day. This is a real correctness defect, not a styling preference: `dayState(for:)` uses `cellDate` to look up sessions; the resulting "done" cell will appear under the wrong weekday letter.

Independently this also means the carousel does not match the `BlockCard` week ticker on Today (which uses `PeriodizationEngine.weekIndex` based on block start, not ISO/locale week).

**Fix:** Pin to a Monday-first calendar in the carousel scope. Either:
```swift
var cal = Calendar(identifier: .iso8601)  // ISO-8601 always uses Monday=2 as firstWeekday
cal.firstWeekday = 2
let start = cal.dateInterval(of: .weekOfYear, for: now)?.start ?? now
```
Or compute `weekStart` deterministically from `now` by subtracting `((weekday + 5) % 7)` days. Then `weekdayLetters` stays "M, T, W, T, F, S, S" and `dayState(for: cellDate)` will resolve consistently.

### CR-02: `BlockOverviewScreen.phaseRow` renders an orphan `ZStack` containing a stray signal stripe rectangle above every "NOW" row

**File:** `fitbod/Periodization/BlockOverviewScreen.swift:474-481`
**Issue:** The `@ViewBuilder` function `phaseRow(...)` builds two sibling top-level views:
```swift
ZStack(alignment: .leading) {
    if isNow {
        Rectangle()
            .fill(Color.bruSignal)
            .frame(width: 4)
    }
}

HStack(alignment: .top, spacing: 10) { ... }
    .overlay(alignment: .leading) {
        if isNow {
            Rectangle().fill(Color.bruSignal).frame(width: 4)
        }
    }
```
The `HStack` already has a correct `.overlay(alignment: .leading)` that draws the 4pt NOW stripe. The preceding `ZStack` is **orphaned dead code that still renders**: under `@ViewBuilder`, the function returns a `TupleView` of `ZStack + HStack`, and the enclosing `ForEach` in `phaseProgressionList` will stack them vertically in the outer `VStack`. The visible effect is an extra ~CGFloat.greatestFiniteMagnitude-tall rectangle sitting above the row (because nothing constrains its height) only when `isNow == true`. At minimum the inner Rectangle has a 4pt width but no explicit height — its layout in a top-level ZStack with no other children will be ambiguous and likely zero-height in practice, but the bug is still present and a future refactor (e.g., adding a sibling to the ZStack) will surface it.

**Fix:** Delete lines 474-481 entirely. The `.overlay(alignment: .leading)` on the `HStack` is the correct, single source of truth for the NOW stripe.
```swift
HStack(alignment: .top, spacing: 10) {
    ...
}
.padding(.horizontal, 16)
.padding(.vertical, 11)
.frame(maxWidth: .infinity, alignment: .leading)
.background(isNow ? BlockPhaseColors.rowTint(for: .intensification) : Color.clear)
.overlay(alignment: .leading) {
    if isNow {
        Rectangle().fill(Color.bruSignal).frame(width: 4)
    }
}
```

### CR-03: `BlockOverviewScreen` captures `weekStart`/`weekEnd`/`todayDate` once at `init`; values become stale across midnight or week rollover

**File:** `fitbod/Periodization/BlockOverviewScreen.swift:48-50, 62-77`
**Issue:** `weekStart`, `weekEnd`, and `todayDate` are declared as `let` stored properties and assigned from `Date.now` in `init`. These values are then used by the `@Query<Session>` predicate (lines 72-77 capture `startBound`/`endBound`) AND by `dayCell(for:offset:)` to compute "today/done/upcoming/rest" state. Because SwiftUI may keep a `View`'s identity stable across body re-evaluations (and the `@Query` predicate is captured at init), once the user opens this screen and leaves it mounted past midnight (or worse, past Sunday/Monday week rollover), the carousel will continue to render the *previous* week's data and label the wrong cell as "TODAY". Several call sites use `Date.now` directly (`dayState(for:)` line 165 uses `cal.isDate(cellDate, inSameDayAs: Date.now)` and `currentWeekIndex` reads `Date.now`), so the screen is *internally inconsistent* — the query bounds are frozen at view creation while the "today" highlight follows wall clock.

**Fix:** Compute `weekStart`/`weekEnd` lazily inside `body` (as a `var`), or rebuild the `@Query` predicate via `.task(id: todayBucket)` where `todayBucket` rounds `Date.now` to the day. The simplest patch: keep `weekStart`/`weekEnd` as computed properties that re-derive from `Date.now`, and recreate the predicate via `@Query(filter:)` recomputed in a `body`-level helper. Note: `@Query` predicate **cannot** be recomputed from a computed property — the proper pattern is to push the parent's `Date` down as a `let` and use SwiftUI's `id:` modifier on the screen to force re-init when the day rolls over, e.g., `BlockOverviewScreen(block:).id(cal.startOfDay(for: .now))`. If a midnight bug is out of scope for v1 (one-user app, screen seldom left open overnight), document this trade-off explicitly with a `// FIXME(v2): predicate frozen at init` comment so the next agent doesn't miss it.

## Warnings

### WR-01: `BlockOverviewScreen.weekCarousel` session-count footer masks `doneCount > scheduledCount`

**File:** `fitbod/Periodization/BlockOverviewScreen.swift:320`
**Issue:** `Text("\(doneCount) / \(max(doneCount, scheduledCount)) SESSIONS DONE")`. When the user logs more sessions than the block has scheduled routines (a perfectly normal scenario — a 3-routine block with 4 sessions this week), the denominator silently equals the numerator and the user sees "4 / 4 SESSIONS DONE" instead of the truthful "4 / 3 SESSIONS DONE". This hides over-reach. The adjacent `leftCount = max(0, scheduledCount - doneCount)` clamps to zero — fine in isolation, but combined with the denominator mask, the user can never see "you did extra work."
**Fix:** Drop the `max(...)`:
```swift
Text("\(doneCount) / \(scheduledCount) SESSIONS DONE")
```
If the intent was to avoid a divide-by-zero or "0/0" empty-block display, add an explicit guard:
```swift
let denominator = scheduledCount == 0 ? doneCount : scheduledCount
```

### WR-02: `BlockOverviewScreen.dayState`/`routineNameForCell` `block.routines` traversal won't match historical sessions whose source routine was deleted

**File:** `fitbod/Periodization/BlockOverviewScreen.swift:170-172, 191-193`
**Issue:** The "done" predicate is `session.block?.id == block.id || (block.routines ?? []).contains { $0.id == session.sourceRoutineID }`. If a routine that was once linked to this block has been deleted (RoutinesListView.handleDelete removes routines from `block.routines`), historical sessions logged under that routine will lose their "done" cell despite `session.startedAt` still being inside the window. Sessions linked via `session.block?.id == block.id` still resolve, but the second clause silently degrades. This isn't a panic but it is a quiet data-display bug for the soft-ref design.
**Fix:** Either (a) accept that "done" only follows `session.block?.id == block.id` (preserves block ownership across routine deletes), or (b) snapshot `sourceRoutineID` into a Set captured once per body evaluation rather than scanning `block.routines` (which may be lazy-loaded by SwiftData). At minimum, document the soft-ref behavior at the predicate site.

### WR-03: `BlockBuilderView` inner List height uses magic-number `count * 120`

**File:** `fitbod/Periodization/BlockBuilderView.swift:304`
**Issue:** `.frame(height: CGFloat(draft.phases.count) * 120)` hardcodes 120pt per row. The actual `BlockPhaseEditorRow` body contains a `Grid` of 3 stepper cells (44pt min button height each), a header row (28pt ordinal + ⋮⋮ glyph), and 12pt vertical padding — at default text size that lands somewhere around 140-160pt, not 120pt. The rows will be visually clipped. Dynamic Type (e.g., a11y XXL) will compound the clip.
**Fix:** Drop the fixed `.frame(height:)` and let the inner List size to content via `.frame(maxHeight: .infinity)` or move from `List` to `LazyVStack`/`ForEach` with separate `.onMove`/`.onDelete` via a custom gesture. The List wrapper is only here for `.onMove`/`.onDelete` mechanics — `LazyVStack` with explicit reorder buttons would remove this entire foot-gun.

### WR-04: `BlockOverviewScreen.computedDaysRemaining` floor/ceil mismatch can produce off-by-one

**File:** `fitbod/Periodization/BlockOverviewScreen.swift:113-121`
**Issue:** The endDate branch uses `Int(ceil(endDate.timeIntervalSince(Date.now) / 86_400))`, while the fallback branch uses `Int(floor(Date.now.timeIntervalSince(block.startDate) / 86_400))`. The fallback computes `totalDays - daysSince` — which combined with `floor` rounds the days-since-start *down* (good — "I'm on day 0 of a 14-day block") but inflates `daysRemaining` by one. The ceil branch rounds *up* toward "you still have one whole day left." A 14-day block started exactly N hours ago will show different "days remaining" between the two branches given the same wall-clock state. Both branches should use the same rounding policy.
**Fix:** Standardize on `Calendar.dateComponents([.day], from:to:).day ?? 0` which avoids the timeInterval/86400 trap and respects DST:
```swift
private var computedDaysRemaining: Int {
    let cal = Calendar.current
    if let endDate = block.endDate {
        return max(0, cal.dateComponents([.day], from: Date.now, to: endDate).day ?? 0)
    }
    let totalDays = MesocycleWeekPage.totalWeeks(of: block) * 7
    let daysSince = cal.dateComponents([.day], from: block.startDate, to: .now).day ?? 0
    return max(0, totalDays - daysSince)
}
```

### WR-05: `BlockCard.weekTickerStrip` clamps to 7 cells but TabView pager iterates `totalWeeks`

**File:** `fitbod/Periodization/BlockCard.swift:139, 104`
**Issue:** `ForEach(0..<min(totalWeeks, 7), id: \.self) { weekIndex in weekTickerCell(...) }` — the ticker shows up to 7 weeks. The TabView pager underneath iterates `0..<totalWeeks` without a cap (line 104), so a 12-week block lets the user swipe to week 8-12 with zero visible indicator in the ticker. This is a UX regression that the audit can't catch, but it's also a real correctness bug: the ticker no longer represents the navigable range. The `BlockContextBand.WeekTickerCells` similarly clamps to 5 (line 105: `min(totalWeeks, 5)`). The behavior should be consistent and either show all weeks (horizontal scroll) or visibly indicate truncation.
**Fix:** Either render the ticker as a `ScrollView(.horizontal)` so all weeks are tappable, or render a "…" sentinel for the truncated tail. The current `min(totalWeeks, 7)` silently hides weeks 8+.

### WR-06: `BlockReviewView.bottomActionBar` "Start next" calls `acknowledge()` but not `acknowledgeAndDismiss()` — block stays active until sheet auto-dismisses

**File:** `fitbod/Periodization/BlockReviewView.swift:290-293, 325-340`
**Issue:** The "Start next ▸" button calls `acknowledge()` (which sets `block.isActive = false` and `block.reviewedAt = now`), then assigns `pendingNextBlockBuilder = BlockTemplates.template(for: recommendedKind)`, which presents the next-block builder sheet. The current sheet (`BlockReviewView`) is **not dismissed** in this path — only the inner sheet for the next block opens. Once the user finishes the new-block builder (dismiss on Save or Cancel), they're returned to the still-mounted BlockReviewView for the now-inactive, reviewed block. This is confusing UX. The intent of `acknowledgeAndDismiss()` (line 337) is precisely this case, but it is never called from `bottomActionBar`. The comment at line 322 says "so 'Start next ▸' can acknowledge THEN show the next-block sheet without an immediate dismiss" — but the implementation leaves the user staring at a completed review screen after dismissing the builder.
**Fix:** After the new-block builder sheet dismisses, dismiss the review sheet. Either dismiss before opening the next sheet (acceptable since the sheet presentation will re-anchor to the parent) or use `.onDismiss` on the inner sheet to call `dismiss()` on the review sheet.

### WR-07: `BlockBuilderView.snapshotHash` includes `Double` multipliers in a `String` interpolation — round-trip drift after format changes

**File:** `fitbod/Periodization/BlockBuilderView.swift:418-424`
**Issue:** `snapshotHash()` builds a comparison key by interpolating `\($0.volumeMultiplier)` and `\($0.intensityMultiplier)` directly. Swift's default `Double.description` is locale-independent but precision-sensitive: `1.0` prints as `"1.0"`, `1.0000000001` prints as `"1.0000000001"`, and any in-place arithmetic (`(x + 0.05).rounded(toPlaces: 2)` in `BlockPhaseEditorRow.volumeCell`) may produce a value that looks the same to the user but hashes differently. The unsaved-changes confirmation will fire even when the user has visually returned multipliers to their initial value via incremental +/− taps. Not a crash, but a real usability defect.
**Fix:** Round to a stable precision before stringifying:
```swift
let phaseHash = draft.phases.map {
    String(format: "%@|%d|%.2f|%.2f", $0.kind.rawValue, $0.weeks, $0.volumeMultiplier, $0.intensityMultiplier)
}.joined(separator: ",")
```

### WR-08: `BlockOverviewScreen.dayCell.accessibilityLabel` chains ternaries with the `state` variable; "rest" gets labeled "phaseKind phase" rather than "rest day"

**File:** `fitbod/Periodization/BlockOverviewScreen.swift:383`
**Issue:** `accessLabel = "\(weekdayLong), \(routineName ?? (state == .rest ? "rest day" : phaseKindCapitalized)), \(state == .done ? "done" : state == .today ? "today" : state == .upcoming ? "upcoming" : "rest")"`. For an `.upcoming` cell with no routine name, the middle slot resolves to `phaseKindCapitalized` (e.g., "Accumulation") — fine. For a `.today` cell, same — fine. For an `.upcoming` or `.today` cell that DOES have a routine name, VoiceOver reads the routine name — fine. But the chain is unreadable and the `state == .rest ? "rest day" : phaseKindCapitalized` branch makes the middle slot say "Accumulation" for a rest day with no routine ONLY IF `state != .rest` … wait, no: `state == .rest ? "rest day" : phaseKindCapitalized` is **inside** `routineName ?? (...)`, so it only fires when `routineName == nil`. If `state == .upcoming && routineName == nil`, the middle slot is `phaseKindCapitalized`. The trailing `state == .done ? "done" : ...` then independently appends "done/today/upcoming/rest". The label is functionally correct but extremely brittle and unreadable; a future edit will almost certainly break it. Also: there is no comma between `routineName` (when present) and the closing state word — e.g., "Monday, Push A, done" reads OK, but if `routineName` is empty/nil it becomes "Monday, Accumulation, upcoming".
**Fix:** Extract a small helper to enumerate the four cases explicitly:
```swift
private func accessibilityLabel(for state: DayState, weekday: String, routineName: String?) -> String {
    let middle = routineName ?? (state == .rest ? "rest day" : phaseKindCapitalized)
    let trailing: String = {
        switch state {
        case .done:     return "done"
        case .today:    return "today"
        case .upcoming: return "upcoming"
        case .rest:     return "rest"
        }
    }()
    return "\(weekday), \(middle), \(trailing)"
}
```

### IN-01: `BlockOverviewScreen.routineNameForCell` returns `String??` flattened to `String?` via `?? nil`

**File:** `fitbod/Periodization/BlockOverviewScreen.swift:189-193`
**Issue:** `.map { $0.routineSnapshotName.isEmpty ? nil : $0.routineSnapshotName } ?? nil` produces a `String??` from the `map` (because the closure returns `String?` and `.map` lifts that into another optional via `Session?`). return weekSessions.first { session in

```swift
    && (session.block?.id == block.id
```


### IN-03: `BRUSectionHead` overlay-Menu pattern in `BlockBuilderView.phasesSection` is brittle

**File:** `fitbod/Periodization/BlockBuilderView.swift:247-270`
**Issue:** The plan calls for a tappable right-side action on `BRUSectionHead`. The implementation passes `rightAction: nil` to `BRUSectionHead` then layers a `Menu` overlay aligned `.trailing` on top of it. The visible "+ ADD PHASE" text inside the Menu uses the same style as `BRUSectionHead`'s tappable variant (bruSignal, labelSmall, tracking 1.2), so the user sees a single button — but accessibility services will announce both the BRUSectionHead's display-only right metadata (because `rightAction: nil` means the BRUSectionHead doesn't render it… actually it doesn't render anything because `right:` is also `nil`-ed via the rightAction nil-check at line 73. Wait — line 247 passes `right: "+ ADD PHASE"` AND `rightAction: nil`, which means the BRUSectionHead WILL render the display-only "+ ADD PHASE" in bruMuted — and the overlay Menu draws a second "+ ADD PHASE" in bruSignal on top of it. Visually the bruSignal Menu wins (rendered last), but the underlying bruMuted text is still in the layout and VoiceOver will read both. Confirmable by inspecting the BRUSectionHead else branch (line 84-91 of BRUSectionHead.swift): when `rightAction == nil`, it renders the display-only right text in bruMuted.
**Fix:** Either pass `right: nil` to the BRUSectionHead and let the overlay carry the entire visual + interaction, or use the existing `BRUSectionHead(_, right:, rightAction:)` API that already supports tappable right actions (lines 73-83 of BRUSectionHead.swift). The cleaner path:
```swift
BRUSectionHead("Phases", right: "+ ADD PHASE", rightAction: {
    // Cannot wire Menu here directly — BRUSectionHead expects a closure not a View.
    // Either (a) lift the Menu into BRUSectionHead's API as a generic rightContent ViewBuilder,
    // or (b) replace the Menu with a sheet/confirmationDialog that fires from rightAction.
})
```

### IN-06: `BRUPeriodizationAuditTests` `forbiddenPatterns` regex for `.font(.title)` uses `\b` which won't anchor on the closing `)`

**File:** `fitbodTests/BRUPeriodizationAuditTests.swift:185`
**Issue:** The regex `\.font\(\.title\b` matches `.font(.title`, `.font(.title2`, etc. — correct intent, but the audit will also match a hypothetical `.font(.titleBar)` that we don't ban. Low-impact since no such pattern is in use, but the regex is sloppier than the surrounding ones (e.g., `.font(.body)` is fully anchored at `\.font\(\.body\)`). Same audit suite also lacks a check for `.foregroundStyle(.primary)` / `.foregroundColor(.primary)` semantic-color leaks — out of scope for v1 but worth a follow-up note.
**Fix:** Optionally anchor more strictly: `\.font\(\.title[0-9]?\)` to catch `.title`, `.title2`, `.title3` explicitly.

### IN-07: `BlockOverviewScreen` Preview uses `try!` for `ModelContainer` initialization

**File:** `fitbod/Periodization/BlockOverviewScreen.swift:573-577`
**Issue:** Standard SwiftUI preview pattern, but `try!` on `ModelContainer(...)` will trap if the schema fails to load. Since Preview crashes are silently swallowed by Xcode (the canvas just goes red), this isn't a runtime concern, but a `try? ` with a `Text("Preview unavailable")` fallback is the more idiomatic safe pattern for previews shipped to other developers.
**Fix (optional):** Wrap in `do { ... } catch { return AnyView(Text("Preview unavailable")) }`.
