### PlateStackViz
```swift
public init(
    platesPerSide: [(weight: Double, count: Int)],
    barLabel: String,
    heightScale: CGFloat = 1.0,
    showLegend: Bool = true
)
```
- `platesPerSide` — heaviest-first denominations and per-side counts
- `barLabel` — bar weight string for accessibility label (e.g. `"45 lb"`)
- `heightScale` — uniform scale multiplier; use `0.3` for WarmupRampRows mini-viz
- `showLegend` — toggles the legend dots row; auto-hidden when `heightScale < 0.5`

### PlateTallyRow
```swift

```
- `weight` — plate weight value
- `count` — `@Binding<Int>` so the row is the input affordance (no Stepper)
- `unitLabel` — `"lb"` or `"kg"` for accessibility label

### PlateStackViz uses HStack layout not Canvas API

**[Rule 1 - Implementation Choice] HStack+Rectangle over raw Canvas — not a bug, a deliberate deviation from plan task title**
- The plan title says "Canvas primitive" but the implementation uses `HStack(spacing:0)` with `Rectangle()` views sized via `frame()` rather than raw `Canvas { context, size in ... }` API
- Reason: SwiftUI's layout system handles the alignment, `heightScale` multiplication flows naturally into `frame()` calls, and the plate rectangles need SwiftUI hit-testing for future interactive variants
- This matches `plate-calc.jsx` which also uses plain `<div>` elements with `width`/`height` styles — no literal canvas
- The 03-UI-SPEC says "Canvas-drawn" conceptually (plate-stack is drawn, not data-driven) not "use SwiftUI Canvas API"; the visual output is identical
- Impact: none — downstream consumers call `PlateStackViz(platesPerSide:barLabel:)` regardless of internal rendering approach
