## Decisions Made

- **Place the two new picker rows inside the existing first Form Section, BETWEEN the Routine Name TextField AND the existing BlockPickerMenu.** UI-SPEC § Header pickers § Final first-Section row order documents exactly this: "Routine Name → Intent → Progression → BlockPickerMenu". A separate Section for the two header rows would introduce a visual section gap mid-header that doesn't match the UI-SPEC contract. Plan-checker WARNING 5 fix anchored this placement explicitly in the plan body.
- **Relocate `snapshotHash()` to RoutineDraft with INTERNAL access.** Internal is the cheapest access level that makes the helper reachable from the unit-test target via `@testable import fitbod`. Public would leak the dirty-check helper as part of RoutineDraft's API surface (it's not part of the public contract — it's a builder-private fingerprint). Private wouldn't let the test target call it. Internal is the right granularity. The method body lifts the existing view-level implementation verbatim plus two new components — the lift is mechanical because the original body already only read RoutineDraft state.
- **Include intent.rawValue + progressionKind.rawValue in the snapshotHash inputs (Phase 3.1 expansion).** Without this, changing an Intent or Progression picker selection would NOT flip the hash, and the user could tap Cancel without seeing the discard-confirmation dialog — silently losing the picker change on dismiss. This is the intended Phase 3.1 behavior change to the dirty-check. Test #6 locks the behavior so a future edit that accidentally drops either component from the hash fails immediately.
- **Both Progression options (Block Periodized + Hybrid) remain selectable in the header picker.** Per D-08 (CONTEXT.md). The existing `ProgressionStrategyFactory.make(for:)` (`fitbod/Prescription/ProgressionStrategyFactory.swift`) routes `.block → BlockPeriodizedStrategy()` and `.hybrid → HybridStrategy()` — both strategies shipped in Phase 3 (per Phase 3's existing factory). The picker selects which strategy `SessionFactory` invokes once per session per D-14. No Phase 3.1 behavior change to the factory. CONTEXT.md D-08's rationale uses some outdated phrasing — see § Threat Flags / Follow-up Items below.
- **Take a Rule 3 minimum-viable removal of the per-exercise Intent + Progression UI from PrescriptionEditorRow.swift + RoutineExerciseCard.swift instead of stopping execution and surfacing a checkpoint.** The plan-as-written assumed those files would compile against the post-Task-1 RoutineExerciseDraft, but removing the fields means PrescriptionEditorRow's `$draft.intent` binding + `$draft.progressionKind` binding + the `progressionSection`'s conditional check on `draft.progressionKind == .block || .hybrid`, AND RoutineExerciseCard's intentChip's `draft.intent.rawValue.capitalized` all become symbol-broken. - **Do NOT update fitbodTests/RoutineDraftValidationTests.swift, fitbodTests/RoutineBuilderCopyTests.swift, or any other test file outside RoutineBuilderHeaderPickersTests.swift.** Test target compile is Plan 08's scope per Plan 03 + Plan 07's SUMMARYs.
