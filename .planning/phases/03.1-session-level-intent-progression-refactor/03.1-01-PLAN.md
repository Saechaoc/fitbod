**Architecture (BLOCKER 3 fix — adopts Apple's documented SwiftData custom-migration pattern):** SwiftData migrations that DELETE properties from existing @Model classes cannot be expressed with shared @Model types across VersionedSchemas. The deleted properties must still exist on the V3-side schema so the willMigrate closure can read them, but the V4-side @Model class must not declare them. The canonical solution is namespaced @Model types per VersionedSchema:

- `SchemaV3` declares **nested standalone @Model classes** for the four affected entities (Routine, Session, RoutineExercise, SessionExercise) in V3 shape — RE/SE retain `intentRaw`+`progressionKindRaw`; Routine/Session don't carry them.
- `SchemaV4` declares **typealiases** to the top-level production types (`typealias Routine = fitbod.Routine`, etc.). The production types are reshaped to V4 shape by Plan 02. At Plan 01 commit time the typealiases resolve against the still-V3-shape top-level types; after Plan 02 lands they automatically reflect the V4 shape.
- The migration's willMigrate closure fetches via `SchemaV3.RoutineExercise.self` (V3 shape, has intentRaw) and writes via `SchemaV4.Routine.self` (V4 shape, has intentRaw on Routine).

This pattern is the documented Apple pattern from WWDC23 "Migrate to SwiftData" + "Adopting SwiftData for a Core Data app" — see also `developer.apple.com/documentation/swiftdata/migrationstage/custom`.

From Apple SwiftData docs:
- `MigrationStage.custom(fromVersion:toVersion:willMigrate:didMigrate:)` runs an arbitrary closure with a `ModelContext`. Inside willMigrate, the context can fetch using EITHER the FROM-schema types OR the TO-schema types — SwiftData merges the schemas for the duration of the stage. This is the load-bearing property that lets the closure fetch SchemaV3.RoutineExercise rows (V3 shape) AND fetch SchemaV4.Routine rows (V4 shape) in the same closure.

Pattern reference (Apple "Adopting SwiftData for a Core Data app"):
```
public static let migrateV3toV4 = MigrationStage.custom(
    fromVersion: SchemaV3.self,
    toVersion: SchemaV4.self,
    willMigrate: { context in
        // Fetch V3-shape rows via the nested types.
        let v3REs = try context.fetch(FetchDescriptor<SchemaV3.RoutineExercise>())
        let v3SEs = try context.fetch(FetchDescriptor<SchemaV3.SessionExercise>())
        // Fetch V4-shape Routine + Session rows via the typealiases. These rows already
        // have the new fields with default values; the closure writes the backfilled values.
        let v4Routines = try context.fetch(FetchDescriptor<SchemaV4.Routine>())
        let v4Sessions = try context.fetch(FetchDescriptor<SchemaV4.Session>())
        for routine in v4Routines {
            let routineV3REs = v3REs.filter { $0.routine?.id == routine.id }
            let intents = routineV3REs.map { $0.intentRaw }
            let progressions = routineV3REs.map { $0.progressionKindRaw }
            routine.intentRaw = Self.modeRaw(of: intents, tieBreak: "strength")
            routine.progressionKindRaw = Self.modeRaw(of: progressions, tieBreak: "double")
        }
        for session in v4Sessions {
            let sessionV3SEs = v3SEs.filter { $0.session?.id == session.id }
            let intents = sessionV3SEs.map { $0.intentRaw }
            let progressions = sessionV3SEs.map { $0.progressionKindRaw }
            session.intentRaw = Self.modeRaw(of: intents, tieBreak: "strength")
            session.progressionKindRaw = Self.modeRaw(of: progressions, tieBreak: "double")
        }
        try context.save()
    },
    didMigrate: nil
)
```

**KEY:** The V4 Routine/Session fields (`routine.intentRaw = ...`) are written via the SchemaV4 typealiased types. At Plan 01 commit time, `SchemaV4.Routine` resolves to `fitbod.Routine` which DOES NOT yet have `intentRaw` (Plan 02 adds it). Therefore the willMigrate closure as written above WILL NOT COMPILE at Plan 01 time. The Task-1 instructions below address this by gating the field-write lines behind a `// TODO(Plan 02): uncomment field writes after Routine/Session model updates land` block — Plan 02 uncomments them when the top-level types gain the fields. The grouping math, FetchDescriptor calls, and helper invocations all compile at Plan 01 time; only the four field-write lines are gated.

The modeRaw helper (deterministic mode-with-tie-break):
```
internal static func modeRaw(of values: [String], tieBreak: String) -> String {
    guard !values.isEmpty else { return tieBreak }
    let counts = Dictionary(grouping: values, by: { $0 }).mapValues(\.count)
    let maxCount = counts.values.max() ?? 0
    let topKeys = counts.filter { $0.value == maxCount }.map { $0.key }
    if topKeys.contains(tieBreak) { return tieBreak }
    return topKeys.sorted().first ?? tieBreak
}
```

This helper is reused by SchemaV4MigrationTests (Task 2). Expose it as `internal static` on FitbodSchemaMigrationPlan so both willMigrate and tests can call it.
