From Apple SwiftData docs (cite in code comment):
- `MigrationStage.custom(fromVersion:toVersion:willMigrate:didMigrate:)` runs an arbitrary closure with a `ModelContext` between the two schema versions.
- willMigrate sees rows under the FROM schema; didMigrate sees rows under the TO schema. The plan uses willMigrate because the backfill source (RoutineExercise.intentRaw, SessionExercise.intentRaw) only exists in V3.

WAIT — the canonical SwiftData custom-migration shape: in willMigrate the OLD-schema data is still present; the new fields can be written if both schemas declare them. The pattern this codebase will follow:
1. SchemaV4 has Routine.intentRaw, Routine.progressionKindRaw, Session.intentRaw, Session.progressionKindRaw declared as NEW fields. RoutineExercise and SessionExercise in SchemaV4 STILL declare intentRaw / progressionKindRaw because they must exist during willMigrate to be read. Wave 2 plan 02 removes them from the @Model class — by then we'll need a SchemaV4 → SchemaV4.1 cleanup, OR the simpler approach: declare the per-exercise raw fields on the schema-only (V3) entity types and drop them from the canonical @Model in V4.

PLANNER NOTE (informational for executor): The simplest viable shape — use SwiftData's native lightweight removal: declare `Routine` and `Session` with the new fields, leave the `@Model` classes for `RoutineExercise` / `SessionExercise` still carrying `intentRaw` / `progressionKindRaw` during the V3→V4 stage so willMigrate can read them, then have Wave 2 plan 02 remove the per-exercise fields. BUT this means the per-exercise field removal must happen in a SECOND stage, V4 → V5.

The CONTEXT.md D-05 / D-07 explicitly says "single stage", and the source-of-truth specifics says "single MigrationStage.custom willMigrate vs split into two stages with intermediate — planner picks the simpler one that the test suite can exercise cleanly."

Executor MUST implement using the following approach: **In SchemaV4, keep the per-exercise raw fields declared on the schema-level types (Routine, Session, RoutineExercise, SessionExercise) so willMigrate can read+write all fields. Wave 2 plan 02 will REMOVE the per-exercise raw fields from the canonical `@Model` classes (which are what the runtime uses for the post-migration store). This is the documented SwiftData pattern — the schema's VersionedSchema model list controls what shape the underlying store has at that version; the canonical `@Model` is the runtime view of the latest version.**

In practice, this means SchemaV4.models references the SAME `@Model` types as SchemaV3 (Routine.self / Session.self / RoutineExercise.self / SessionExercise.self) — just like SchemaV3.models inherits SchemaV2.models. The runtime types (which Wave 2 modifies) end up being the SchemaV4-shaped types after Wave 2 lands.

**Custom migration approach for THIS plan (Plan 01):**
The V3→V4 stage runs WHILE the runtime types still carry the V3 shape (per-exercise raw fields still on RoutineExercise / SessionExercise — Wave 2 hasn't run yet). Wave 2 plan 02 makes the FINAL @Model shape match SchemaV4 (Routine/Session add the fields; RoutineExercise/SessionExercise drop them).

Therefore: Plan 01 lands SchemaV4 + migration WITH the assumption that the post-migration runtime types carry the V4 shape (which Wave 2 will install). The migration test in Plan 01 cannot exercise the END-TO-END migration because Routine/Session don't yet have the destination fields at the @Model level. The migration test in Plan 01 verifies migration plan WIRING (3 schemas registered, 3 stages, V3→V4 stage is custom). The END-TO-END backfill behavior is tested in Plan 02 (after the model fields land) via a dedicated `migratesV3RoutineToV4WithBackfill` test that uses a fresh container against `Schema(SchemaV4.models)` and exercises the willMigrate closure with seeded V3-shape data.

This is also what the orchestrator's suggested breakdown says: "Plan 03.1-01: SchemaV4 + custom migration + SchemaV4MigrationTests" + "Plan 03.1-02: Model updates ... + computed accessors" — the model updates land in Plan 02. The migration tests in Plan 01 cover what can be verified independently; Plan 02 will EXTEND `SchemaV4MigrationTests` with the round-trip + backfill tests once the model fields exist.
