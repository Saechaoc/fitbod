## Decisions Made

- **Use the SIMPLEST descriptor + post-filter approach in PreviousMatchingIntent per D-13.** The plan documented three options: (1) build the #Predicate over Session instead and flat-map to SessionExercise, (2) keep filtering by intentRaw in #Predicate (impossible — the field doesn't exist), (3) drop the #Predicate filter entirely and post-filter both gates in Swift. D-13 chose option 3 verbatim; the plan executes it verbatim. This loses the index acceleration on intentRaw (the field is gone from SessionExercise anyway); the new Session.intentRaw #Index doesn't help because the descriptor still fetches SessionExercise rows. At single-user single-month-of-data scale the cost is sub-millisecond. A future Phase 6 optimization could switch to fetching matching Sessions first if performance becomes an issue.
- **Mirror SessionFactory.fetchHistoryPoints / lastSessionWorkingReps's exact shape inside PreviousMatchingIntent.** Plan 03 already established the pattern (descriptor with no intent filter + Swift post-filter on multi-level optional chain). Plan 07 closes the temporary asymmetry that Plan 03's SUMMARY documented — at Plan 07 close, all three queries are structurally identical. This makes the Pitfall 1 workaround auditable across the codebase and establishes the pattern for any future intent-on-Session query.
- **Keep ExerciseHistoryView's `\\.session?.startedAt` SortDescriptor in place.** The plan documented a fallback (Swift-side sort) in case the SortDescriptor's multi-level optional keypath tripped Pitfall 1 after Plan 02's schema reshape. xcodebuild on the iPhone 17 simulator compiles cleanly — the only remaining errors are 4 in RoutineDraft (Plan 04 scope). The fallback was not needed; documented its shape in an inline comment for future toolchain-regression resilience but did not exercise it.
- **PrescriptionExplanation.sessionIntent is a var, not a let.** The field must be mutable because callers (SessionFactory + SessionExerciseCard.currentExplanation) set it AFTER `strategy.prescribe()` returns. The pattern is `var enriched = explanation; enriched.sessionIntent = se.session?.intent; return enriched` — wouldn't work if sessionIntent were `let`. This is consistent with the other mutable fields on PrescriptionExplanation (`lastSessionLine`, `computedLine`, `bumpOccurred`, `range`, `phaseContextLine`, `deloadNoteLine`).
- **Strategies do NOT set sessionIntent.** Per the plan's principle: the ProgressionStrategy protocol contract is "history + scalars + plates + bar + block + date → weight + explanation"; introducing Intent into the protocol would couple every strategy to a SwiftData-adjacent enum it doesn't need. The caller-decorates-after-return pattern keeps strategies pure and decoupled (FOUND-07).
