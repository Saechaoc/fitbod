# Phase 3.1 — UI Design Contract

> Visual and interaction contract for the Session-Level Intent & Progression refactor. Generated by gsd-ui-researcher.

This phase is a **mechanical refactor**, not a new design surface. It hoists `intent` and `progressionKind` from per-exercise (`RoutineExercise` / `SessionExercise`) to session-level (`Routine` / `Session`). The user-visible deltas are deliberately small:

1. **`RoutineBuilderView` gains two header pickers** — Intent + Progression — rendered as `LabeledContent` rows immediately under the Routine Name field, ABOVE the Exercises section. They reuse the Phase 3-fix `LabeledContent { Picker(...).pickerStyle(.menu) }` layout verbatim.
2. **`PrescriptionEditorRow` strips two rows** — the per-exercise Intent picker and Progression picker disappear; Sets / Reps / Target RPE / Rest / Tempo toggle / Track partial reps / Auto warm-up / Per-set overrides remain in the same order.
3. **`SessionLoggerView` header gains an intent chip** — rendered next to the elapsed-time `.toolbarItem(.principal)` block (or the toolbar subtitle), reusing the Phase 2 `intentChip` styling (15%-opacity accent capsule, accent caption label).
4. **`RoutineExerciseCard` header strips its intent chip** — intent is session-level now, so per-exercise chip on each builder card is removed (the empty space collapses to the prescription summary line alone).
5. **`WhyThisWeightSheet` status row copy updates** — reads `"{Intent.capitalized} session — {status copy}"` instead of the bare status string.
6. **`IntentChip` extraction** — Phase 2's inline `private var intentChip` on `RoutineExerciseCard` (and `ExerciseHistoryRow`) is promoted to a shared `Views/IntentChip.swift` SwiftUI view with one initializer `IntentChip(intent: Intent)`. Both Phase 2 surfaces (history-row inline badge stays neutral gray) AND the new `SessionLoggerView` header chip (accent capsule) reference it. The styling is **the accent-capsule variant**; the neutral history-row variant is a separate inline view that stays in `ExerciseHistoryRow.swift` (no behavior change for history).

The design stance is identical to Phases 1–3 verbatim: **"comprehensive but uncluttered"** — progressive disclosure as the tie-breaker. Phase 3.1 reduces per-row clutter on the routine builder (two rows removed) and adds one chip to the session header — a net simplification.

This UI-SPEC carries forward every token from Phases 1–3 (`01-UI-SPEC.md`, `02-UI-SPEC.md`, `03-UI-SPEC.md`) **verbatim**: accent `#0E7C86` / `#3FBFC9`, the 8-point spacing scale with 44pt HIG exception, the 4-role / 2-weight semantic typography, the 60/30/10 color split, and the terse-prescriptive copywriting voice. Nothing below restates a prior token unless it changes; the **Component Inventory** and **Copywriting Contract** sections enumerate the deltas only.

The chip is informational; the toolbar `.principal` block as a whole satisfies 44pt for any hit-test concerns SwiftUI imposes on toolbar items.

### Migration UX — copy contract

The SchemaV4 custom migration is **not user-facing** in this v1. There is no migration progress sheet, no migration-result banner, no "Your data was migrated" toast. The user installs the app, the migration runs silently at first `ModelContainer` instantiation, and the user sees a fresh app whose Routines + Sessions carry the backfilled session-level Intent + Progression values. Per `03.1-CONTEXT.md` specifics: "The on-disk store has a fresh SchemaV3 DB (user wiped + reseeded earlier today). The custom migration is exercised only in tests; production users won't have V3 data to migrate when this ships (because v1 hasn't shipped)."

**No migration copy is added.** If a future v1.x release surfaces a migration-aware UI, that copy will be specified in that phase's UI-SPEC — not here.

### Defaults shown in pickers on new routines / fresh sessions

Per D-03 and D-04 (CONTEXT.md):

- A new Routine (created via "+ New Routine" in `RoutinesListView`) renders the Intent picker with "Strength" selected and the Progression picker with "Double Progression" selected. The user can change either before saving.
- The user's selection is persisted through `RoutineDraft.intent` and `RoutineDraft.progressionKind` (D-09); the three-way merge `save(into:context:)` writes these values to the underlying `Routine` row.
- `SessionFactory.start(routine:on:context:)` then snapshots both values to the new `Session` at session start (D-14 + PIVOT-02).

| Element | Default value (new routine) | Visible copy in picker |
|---------|-----------------------------|-----------------------|
| Intent default | `.strength` | "Strength" |
| Progression default | `.double` | "Double Progression" |

### Error / blocked states — none introduced

Phase 3.1 introduces **no new error surfaces, no new empty-state surfaces, no new validation alerts.** The refactor is mechanical. The existing Phase 2 routine-save-failure copy and Phase 3 prescription-unavailable fallback carry forward unchanged.

### Destructive actions — none introduced

Phase 3.1 introduces **no destructive UI actions.** The SchemaV4 migration is a non-interactive schema operation; the only data "destruction" is the removal of `RoutineExercise.intentRaw`, `RoutineExercise.progressionKindRaw`, and `SessionExercise.intentRaw` fields, which is invisible to the user (the data is backfilled to Routine/Session before the per-exercise fields are dropped). Per `03.1-CONTEXT.md` D-06 / D-07, the backfill uses the most-common per-exercise value, with `.strength` / `.double` as deterministic tie-breakers.

## Interaction Patterns

### Routine builder header pickers flow

1. User taps "+ New Routine" in `RoutinesListView` → `RoutineBuilderView` opens with `Form` showing: Routine Name (empty) → **Intent ("Strength")** → **Progression ("Double Progression")** → Folder ("Unfiled") → Exercises (empty).
2. User taps the Intent row → SwiftUI `.menu` picker opens with the 5 intent options. User picks one → menu closes, trailing value updates.
3. Same flow for Progression row.
4. User adds exercises via inline `.searchable` (unchanged from Phase 2). Each `RoutineExerciseCard` shows the prescription summary line WITHOUT an intent chip (the chip is gone — intent is session-level now).
5. User taps "Save" → `RoutineDraft.save(into:context:)` writes `routine.intent` and `routine.progressionKind` along with the existing fields. Three-way merge applies as before.

### Session start + header intent chip flow

1. User taps "Start Workout" on a routine row → `SessionFactory.start(routine:on:context:)` runs.
2. The factory snapshots `routine.intentRaw` → `session.intentRaw` and `routine.progressionKindRaw` → `session.progressionKindRaw` (D-14, PIVOT-02). Subsequent edits to the routine do NOT alter the session's intent/progression.
3. `SessionLoggerView` opens. The principal toolbar block renders:
   - Line 1: "Workout" (`.font(.headline)`)
   - Line 2: routine snapshot name (`.caption .secondary`)
   - Line 3: `IntentChip(intent: session.intent)` — accent capsule, e.g. "Strength"
4. The chip is **read-only**. Tapping it does nothing in v1 (mid-session intent change is explicitly deferred per CONTEXT.md `<deferred>`).

### "Why this weight?" sheet — status row flow (delta only)

1. User taps the `info.circle` icon on a working `SetRow` → `WhyThisWeightSheet` slides up (unchanged from Phase 3).
2. The sheet renders the existing rows (Last session / Formula / Computed / Rounded).
3. **NEW in 3.1:** the Status row at the bottom of the sheet reads `"{Intent.capitalized} session — calibrating (4 / 10 sets)"` or `"{Intent.capitalized} session — calibrated"`, sourced from `PrescriptionExplanation.sessionIntent` + the existing calibration status enum.
4. If `wasManualOverride == true`, the existing "Use Suggested Weight" button appears below (unchanged).

### History view — intent split flow (no visible change)

1. User navigates to an Exercise detail → "View All History" → `ExerciseHistoryView` opens with the existing 6-chip filter row at top.
2. User taps a filter chip → the inner `FilteredHistoryList` rebuilds its `@Query<SessionExercise>` predicate.
3. **DELTA (invisible to user):** the predicate now post-filters on `entry.sessionExercise?.session?.intentRaw == targetIntent` instead of `entry.sessionExercise?.intentRaw == targetIntent`. Same result for matching-intent sessions; different field source.
4. Each row in the list shows the existing neutral inline intent badge (unchanged).

### SchemaV4 migration flow (silent)

1. User taps the app icon → SwiftData instantiates `ModelContainer` with `Schema(SchemaV4.models)` and the `FitbodSchemaMigrationPlan` containing the new V3→V4 custom stage.
2. The custom migration `willMigrate` closure (per `03.1-CONTEXT.md` specifics):
   - Iterates `Routine`s — computes each routine's most-common per-exercise intent + progression from its `RoutineExercise` set; writes to `routine.intentRaw` / `routine.progressionKindRaw`. Ties → `.strength` / `.double`.
   - Iterates `Session`s — computes each session's most-common per-exercise intent + progression from its `SessionExercise` set; writes to `session.intentRaw` / `session.progressionKindRaw`. Ties → `.strength` / `.double`.
3. Per-exercise fields (`RoutineExercise.intentRaw`, `RoutineExercise.progressionKindRaw`, `SessionExercise.intentRaw`) are dropped post-migration.
4. **No UI surface.** User sees the app launch normally; Routines + Sessions render with backfilled session-level values.
